# fp_tool — 音频指纹检索工具

对音频素材库（如游戏音频解包目录）建立指纹索引，再用任意长度的样本音频（短切片、长混剪、录屏提取、重编码 MP3 等）检索定位：
- **短切片** → 定位源文件 + 文件内精确偏移（1~5s 切片误差 ≤0.3s）
- **长样本（拼接/混剪）** → 一次性列出其中包含的**所有**库文件及各自位置，可按样本时间线拼接还原
- **库内共享内容** → 自动发现（同一音效内嵌在多个文件、文件间重复内容等）

纯本地运行，无服务依赖，数据存 SQLite 分片，全库 15,150 文件、3.57 亿条指纹哈希。

## 2. 快速开始

### GUI（推荐）
```bash
python fp_tool\gui.py              # 使用默认索引 fp_tool\index
python fp_tool\gui.py --db 别的索引目录
```
操作：选样本 → 匹配 → 结果表按置信度排序。双击行播放源文件；"导出拼接"按样本时间线还原；"从/到"可只匹配长样本的局部；"最低置信度(%)"留空为自动。

### CLI
```bash
# 匹配
python fp_tool\match.py 样本.mp3
python fp_tool\match.py 样本.wav --from 10 --to 20          # 只匹配 10~20s 段
python fp_tool\match.py 样本.wav --export 还原.wav          # 拼接还原
python fp_tool\match.py 样本.wav --json 结果.json           # 机器可读结果
python fp_tool\match.py 样本.wav --min-aligned 20 --min-ratio 0.03   # 收紧阈值

# 建索引（并行、断点续建）
python fp_tool\build_index.py 音频目录 --out index --workers 10
python fp_tool\build_index.py 音频目录 --out index          # 再次运行=续建
```

### 输出字段
| 字段 | 含义 |
|---|---|
| 文件内偏移 | 样本起点（t=0）对应库文件内的秒位置 |
| 样本区间 | 样本中实际对齐上内容的起止（秒） |
| 命中数 | 对齐到同一偏移的哈希票数（核心证据） |
| 置信度 | 命中数 / 样本总哈希数 |

## 3. 核心原理

### 3.1 指纹提取管线（`fp_core.extract_hashes`）

```
音频 → 重采样 11025Hz 单声道 (soxr_hq) → STFT(1024/256, 43帧/秒)
    → 幅度转 dB (ref=文件峰值, 底噪 -80dB)
    → 2D 局部极大值 (5×5 maximum_filter)
    → 逐帧相对窗口: 保留 ≥ max(帧峰值-12dB, -65dB) 的局部极大值
    → 每帧按幅度保留 top-3（秩选择）
    → 峰值配对: 每个锚点与其后 ≤25 个峰配对, dt∈[2,4095] 帧
    → 30-bit 哈希: (f1<<21)|(f2<<12)|dt   (f1,f2: 9bit 频点, dt: 12bit)
```

**两个关键不变性设计**（决定了低置信度场景仍能命中的根本原因）：

1. **音量不变性**：阈值是"帧内峰值 - 12dB"的**相对**窗口，峰选择是**帧内按幅度排名**，而不是绝对 dB 阈值。因此"安静片段"和"响片段"提取出完全相同的峰集合——背景氛围音（远低于文件峰值）也能入库、能命中；库文件与样本整体响度差异不影响匹配。
2. **时间原点不变性**：选择完全按帧进行（每帧独立 top-3），不含任何按绝对时间对齐的窗口。若用"每秒取 top-N"这类全局窗口，切片窗口边界与文件窗口错位会破坏指纹一致性（本项目曾实测因此出现大面积漏配，逐帧方案后彻底解决）。

静音帧（相对文件峰值低于 -65dB）自动排除，避免 -80dB 底噪产生无意义哈希。

**密度与索引体积**：约 900~1300 哈希/秒/文件（受内容复杂度影响），全库 15,150 文件共约 3.57 亿条。

### 3.2 索引存储

- **分片**：按文件名 md5 均分到 N 个分片（默认 10），每分片一个 SQLite 文件 + 一个 `.dat` 二进制文件。
- **全局 fid**：`fid = (shard_id << 24) | 本地自增id`。⚠️ 必须全局唯一——若用分片内局部 id，跨分片会互相覆盖（曾导致结果错乱）。
- **SQLite 结构**：
  ```sql
  CREATE TABLE files(fid INTEGER PRIMARY KEY, name TEXT, path TEXT, duration REAL, status INTEGER);
  CREATE TABLE hashes(h INTEGER, fid INTEGER, t INTEGER);   -- 建库完成后 CREATE INDEX ix_h
  ```
- **`.dat` 快速加载**：每行 3×int32（h/fid/t）= 12 字节，`np.fromfile` 秒级读入。仅靠 SQLite 逐行读取 3.57 亿行需约 9 分钟，`.dat` 使全库载入降至 **44 秒**。SQLite 保留作元数据与回退。
- **加载内存**：`h + fid + t + 排序索引` 各 8B ≈ 32B/行 → 全库约 12GB（32GB 内存机器无压力）。

### 3.3 匹配算法（`fp_core.match_index`）

1. 样本指纹化，按哈希值分组（hash → 样本帧列表）。
2. 对每个分片：哈希值在排序数组上二分查找（`searchsorted`），得到所有 (fid, t_f) 命中行。
3. **偏移对齐投票**：对每个 (fid, t_f, t_q) 计算 `delta = t_f - t_q`，累加 (fid, delta) 桶的票数，同时记录该桶覆盖的样本帧 min/max。
4. **簇聚类**：同一 fid 的相邻 delta（容差 ±2 帧 ≈ ±46ms）合并为一个命中簇；簇内**票数最高的桶决定偏移**，总票数为簇强度。同一文件在样本中出现多次（重复段落）会聚成多个独立命中。
5. 阈值过滤：`floor = max(min_aligned, ceil(样本总哈希数 × min_ratio))`。
6. 偏移换算：`文件内偏移 = delta × 帧长`（样本 t=0 对应的库文件时刻）。

**抗碰撞分析**：3.57 亿哈希分布在 2^30 空间中，单条查询哈希的随机碰撞期望 ≈ 0.33；真实命中数百上千票集中在唯一 delta 上，随机噪声散布在随机 (fid, delta) 桶上（每桶 1~2 票），信噪比极高。库内大量共享内容（同一音效重复出现在许多文件）会抬高噪声基线，但真实命中仍以绝对票数胜出。

### 3.4 阈值自适应（`min_ratio=None` 时）

```
dur_est = 样本哈希数 / 900
min_ratio = clamp(0.001, 0.008, 3.0 / dur_est)
```

- 短切片（几秒）→ 比例高（0.8%），严格去噪，避免结果刷屏；
- 长样本（几十分钟）→ 比例低（0.1%），避免把其中较短的内嵌片段漏掉（10s 的片段在 2 小时样本里只占 0.1% 级票数）。
- 另设绝对下限 `min_aligned=8` 票，保护极短切片。

### 3.5 拼接还原（`export_stitch`）

按样本时间线顺序，对每个命中簇从**库文件**（干净音源）裁剪 `[偏移-0.2s, 偏移+跨度+0.2s]`，统一重采样到 48kHz 后顺序拼接输出为一个 wav——把混剪/录屏里的原始素材还原出来。

## 5. 参数调优（`fp_core.py` 常量）

| 常量 | 默认 | 作用 | 调大/调小的后果 |
|---|---|---|---|
| `SR / N_FFT / HOP` | 11025/1024/256 | 指纹分辨率 | 提高 SR 更精细但更慢更占空间 |
| `PEAK_WINDOW_DB` | 12.0 | 帧内相对窗口 | 调大→峰更多→更敏感但体积↑ |
| `PEAK_PER_FRAME` | 3 | 每帧峰数上限 | 调为 2 → 索引约缩 1/3（降精度） |
| `PAIR_WINDOW` | 25 | 配对峰数 | 调大→每峰哈希更多→更鲁棒但体积↑ |
| `DEFAULT_MIN_ALIGNED` | 8 | 绝对票数下限 | 调大→结果更少更严 |
| `HASHES_PER_SEC` | 900 | 时长估计常量 | 影响阈值自适应曲线 |

索引体积 ≈ `音频总时长 × 1000~1300 × 12B`（.dat）。若要缩小体积，优先降 `PEAK_PER_FRAME` 或 `PEAK_WINDOW_DB`，然后重建。

## 6. 已知行为与限制

1. **库内共享/重复内容极多**（已用波形互相关验证，相关度 0.4~0.83）：同一文件会在结果中多次出现（每处重复位置一行）、多个文件命中同一内容。这是正确行为——"找出所有相关文件"正是设计目标。判断主命中：票数最高的行；有疑义时播放核对。
2. **静音无法匹配**：低于 -65dB 的内容不产生指纹；文件开头若有静音段，样本区间起点会相应延后。
3. **变速/变调无法匹配**：指纹对音高与速度敏感，加速/降调后的音频需先还原速度。
4. **重编码压低置信度**：MP3 低码率/再次压缩会破坏频谱细节，置信度可能只有 5~15%，但只要第 1 名与第 2 名有明显断层（≥2~3 倍），即可信。
5. **重复性强的音乐**（BGM 循环）偏移存在歧义：切片旋律与多次出现的小节都能对齐，系统会并列列出，最强簇通常是最干净的一次出现。

## 7. 开发与测试

```bash
python fp_tool\test_precision.py --nfiles 60     # 建 60 文件测试索引并跑 36 项回归
python fp_tool\verify_full.py                    # 全量索引抽查（1/3/5s 切片 + 长拼接）
python fp_tool\xcorr.py 另一个文件.wav           # 波形互相关，验证两文件是否真共享内容
```

开发过程中的关键 bug 修复记录（均有对应回归）：
- 分片内 fid 重复导致结果串文件 → 全局 fid 编码
- 绝对 dB 阈值导致安静片段无法命中 → 逐帧相对窗口 + 秩选择
- 0.25s 预算窗口破坏时间原点不变性 → 逐帧 top-3
- 偏移公式错误（`tq0+delta`）→ `delta` 即文件偏移
- 聚类槽位错位（min_tq/strong 写反）→ 修正索引
- Tkinter 跨线程 `after()` 不安全 → queue + 主线程轮询
